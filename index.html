03 / 标准化连接

先确定不同服务如何承接

商品推荐、物流查询、订单确认等服务很难只靠文本表达；平台需要一套成熟、可复用的结果承接方式。

业务难点

行业与任务差异大查询、浏览、确认和交易的字段、状态与操作不同
供给将持续增加逐家设计与开发会使交付成本随品牌数量线性增长
统一体验与个性逻辑并存既要符合千问规范，也要允许企业承载自身业务规则
核心问题不同复杂度的服务，应通过什么形式、如何承接？

先划清卡片、模板与 H5 的边界，再建设规模化交付方案。

调研验证对比微信开发者平台、开放平台 Skill / MCP、开源协议与小微助手方案，重点判断输出稳定性、交互复杂度与接入成本。
固定模板

复用稳定，适合结构明确的信息服务。

H5 容器

灵活但成本高，承接复杂流程与个性逻辑。

动态 A2UI

首期稳定性与治理成本暂不满足要求。

关键判断

模板承接稳定部分，H5 承接复杂流程。

这一步不是先画模板，而是先判断通过什么形式、如何承接。我补充调研了微信开发者平台、开放平台与开源 MCP 和 Skill，也结合小微助手及三方方案观察真实输出。按只读查询、轻交互、单次写入和复杂多步骤做分层后，我判断首期先用模板承接结构稳定的查询与浏览，复杂交易继续交给 H5。

数据上，从广场曝光到首次对话的累计转化只有 1.70%，其中进入分身后超过 85% 的用户没有发送 Query。旧版更像品牌展示页，用户知道谁在这里，却不知道能做什么以及第一句话怎么问。

04.1 / 方案发散

先把旧版问题变成可讨论的方向

我将旧版线上方案与运营、能力、活动、个人等多种组织方式放在同一张图中比较，推动团队从“改样式”转向讨论“用什么心智组织供给”。
起点

旧版以品牌列表为主

发散

围绕不同业务目标生成多版方案

运营位、能力入口、活动主题与个人常用，各自优化不同目标，也暴露不同的扩展成本。

关键判断

页面形态背后是供给组织逻辑

不能只比较视觉好不好看，需要比较用户心智、任务启动、供给扩展和运营成本。

在数据定位后，我先把旧版线上方案和多种短期方向放到同一套界面中比较。这个过程让我意识到，广场改版不是换一种卡片样式，而是在选择供给组织逻辑，因此后续评估的重点是用户心智、任务启动、供给扩展与运营成本。

04.2 / 方向判断

从用户心智出发，收敛到场景优先

结合数据、社媒反馈与竞品调研，我从场景、个人和运营三种心智发散方案，再用理解效率、任务启动与供给扩展逐步收敛。
方案 A · 最终选择

场景优先

先回答用户现在想做什么，再匹配能完成任务的品牌能力；更符合“任务找能力”的入口逻辑。

方案 B

个人优先

围绕常用与历史任务组织，路径直接，但依赖更成熟的个性化信号与供给。

方案 C

运营优先

适合阶段性活动与重点供给，但长期容易让页面被运营内容主导。

我输出了品牌、个人任务和场景三类方向，并用理解效率、任务启动、供给扩展和运营成本评估。品牌优先无法解决能力翻译，个人优先依赖较强个性化和运营能力，最终选择场景优先。

07 / 对千问的建议

下一步：从连接能力，走向放大个人生产力

千问已经建立 Agent / Skill 接入基础；下一阶段不只是连接更多服务，而是理解未完整表达的目标，持续管理用户愿意托付的事情。
当前基础

响应显性指令

用户提出任务，千问选择 Agent / Skill 并完成一次服务。

下一阶段

理解未完整表达的目标

识别潜在需求，决定追问、建议还是准备，再让用户确认边界。

长期方向

持续管理一类事情

从办完一次任务，升级为跟进状态、变化和后续动作。

01
需求找到能力

从服务推荐走向用户代理

先判断真实需求与信息是否充分，再追问、匹配能力并请求确认，避免把主动服务变成广告。

02
责任留存

不是留住人，而是留住事情

围绕行程、订单、学习、项目等长期事务持续跟进；用户无需一直停留，但会持续回来处理事情。

03
任务生长内容

结果即内容，流程即能力

任务结果沉淀为内容或工作流，经分享和调用产生新需求，形成比独立 Feed 更统一的增长链路。

P0可靠执行与长期状态
P1目标识别与主动确认
P2资产分发与价值回流
差异化心智：豆包更擅长争夺注意力；千问更值得争夺用户愿意长期托付的责任。
结合前面的判断，我认为千问下一步应该让需求找到能力，而不是让服务主动找人。首先识别用户未完整表达的目标，再判断是追问、建议还是准备，并由用户确认。留存也不一定来自内容消费，更可能来自责任留存：不是把人一直留在千问里，而是把用户愿意托付的行程、订单、计划和项目留在千问里。内容仍然重要，但应该从任务和关系中自然生长，让结果成为内容，让过程成为可复用能力。
